## AI 回复 1

先给结论：你列的三个现象里，第 1、2 条在当前 HEAD 上已经修掉了；第 3 条只修了一半——P0/P1/P2 的大组是对的，但同一优先级内部没有按工作量排。所以这次不需要重写评分，只需要补排序和补边界测试。

### 1. 先看代码现状

- `apps/server/src/engine/scoring.ts:82-96`：五维基线 `BASE` 与权重 `WEIGHT`（创新 22%、可行 22%、证据 26%、表达 14%、合规 16%）。
- `scoring.ts:98-100`：罚分 `PENALTY = { high: 7, medium: 4, low: 2 }`，单维封顶 `DIMENSION_CAP = 16`。
- `scoring.ts:195`：`value -= Math.min(DIMENSION_CAP, deducted)`，随后夹在 48–93。
- `scoring.ts:146`：风险按标题去重，`if (risks.some((r) => r.title === TITLE_OF[issue])) return;`。
- `scoring.ts:214-241`：修改项先取高风险、再取其余，然后做标题去重；复核时这段没有二次排序，P0 内部按风险生成顺序排列。
- `apps/server/src/report.ts:34` 与 `apps/web/src/pages/ReportPage.tsx:221`：Markdown 导出和前端报告页都按 `session.revisions` 原顺序渲染，自己不做排序。问题源头在 `scoring.ts`，不在渲染层。
- `scoring.test.ts`：复核时只有 2 条测试，一条查“标题不重复 + 分数在 50–90”，一条查脚本轮次；没有封顶边界、没有跨 claim 去重、没有排序断言。

### 2. 三个现象的具体问题

**（1）扣分公式：旧版是“按条累加”，没有单维上限**

当前公式可以写成：

```text
raw   = Σ PENALTY[risk.level]
dim   = round(clamp(BASE[dim] - min(16, raw), 48, 93))
overall = round(Σ dim × WEIGHT[dim])
```

旧版用的是 `high: 9 / medium: 5.5 / low: 3`，且直接 `value -= deducted`。证据强度只要同时命中“缺少基线、样本不足、因果化”三条高风险，原始扣分就会超过 20；如果同一个 `no_baseline` 还被 3 个 claim 各计一次，扣分继续叠加，76 分被压到 42 并不奇怪。这个 42 不是“材料证据真的很差”的稳定判断，而是重复计罚的产物。

所以校准方向不是把 `BASE` 调高，也不是在代码里写 `if (project.name === '智巡校园') overall = 71`，而是把单维扣分封在 16 分：`76 - 16 = 60`。证据强度仍然是五维里最低的，但不会因为同一条缺口被数了三遍而失真。

补充一点：当前 `BASE` 最低是 76，封顶 16 后单维最低也有 60，`Math.max(48, ...)` 这个下限实际上不会触发，保留它只是防御性写法，不是分数被“托底”的原因。

**（2）去重：旧版按 claim × issue 生成，三条同名风险会各扣一次**

旧逻辑是：

```text
for claim of pool:
  for issue of claim.issues:
    risks.push({ title: TITLE_OF[issue], ... })
```

三个不同 claim 都命中 `no_baseline` 时，就会生成三条一模一样的“量化结论缺少基线”；修改项又从风险 1:1 映射，于是出现三条同名 P0。当前代码在 `scoring.ts:146` 用标题做幂等，修改项在 `scoring.ts:236-240` 再用 `usedRevisions` 去重，同一条缺口只会保留一条。`seen` 那个 `claim.id:issue` 集合现在是冗余保护，不影响结果。

**（3）排序：P0/P1/P2 分组有了，但组内没有按工作量排**

修改前的构造顺序是：

```ts
highRisks.concat(risks.filter((r) => r.level !== 'high')).slice(0, 8)
```

它只保证“高风险在前”，P0 内部仍然是风险生成顺序。示例项目实际跑出来是：

```text
P0/高  做归因拆解或降级结论
P0/中  补齐基线对照与置信区间
P0/低  补充样本构成与分层结果
P0/低  把承诺性指标改为阶段目标
P0/中  补齐复现包与权限说明
P1/低  为每个数字补原始记录
```

P0 里高/中/低混排，同一优先级内也没有“先做低工作量”的稳定规则。`report.ts` 和 `ReportPage` 都按数组顺序渲染，所以页面上的顺序会随风险插入顺序变化。这就是“排序不稳定”的直接原因。

### 3. 最小校准方案

1. **保留 16 分封顶**：不调 `BASE`、不调 `WEIGHT`、不调 7/4/2；只把 16 提成 `DIMENSION_CAP` 常量，补注释。
2. **保留标题去重**：风险层和修改项层各保留一次；补一条“三个 claim 命中同一 issue 只出一条”的测试。
3. **加显式排序**：`P0 → P1 → P2`，同优先级内 `低 → 中 → 高` 工作量，再按预计提分降序、标题升序兜底；排序后再截 6 条并重排 `v1..v6`。
4. **补边界测试**：单维封顶、跨 claim 去重、排序三条。

不新增项目分支，不按项目名/材料名改分数。

### 4. 预测

按当前示例材料（12 个 claim、27 轮标准质询）预测：

- 总分 **71**；
- 风险 **6 条**（5 高 / 1 中），标题唯一；
- 证据强度 **60**（3 条高风险，原始扣 21，封顶 16）；
- 合规与复现 **61**（2 高 + 1 中，原始扣 18，封顶 16）；
- 修改项 6 条（P0 ×5、P1 ×1）。

关于你记的 66/42：这是 `docs/prompts/04-scoring.md` 里 11-02 初版记录的现象，不是当前 HEAD 的输出。我把旧参数回退到同一份示例材料上跑了一遍，得到的是 **67 / 48 / 7 条（1 组同名“样本代表性不足”）**，不是 66/42——因为 claim 解析器也改过，同一条基线缺口已经不会再被拆成 3 个 claim。但根因是一样的：重复风险逐条累加且不封顶。当前 HEAD 的实测是 71/60/6，下面按这个口径继续。

### 1. 代码改动

`apps/server/src/engine/scoring.ts`：

```ts
const PENALTY = { high: 7, medium: 4, low: 2 } as const;
// 单维最多扣 16 分：防止一个缺口把整维打到地板，也避免重复风险叠加成“判死刑”。
const DIMENSION_CAP = 16;

const PRIORITY_RANK: Record<Revision['priority'], number> = { P0: 0, P1: 1, P2: 2 };
const EFFORT_RANK: Record<Revision['effort'], number> = { 低: 0, 中: 1, 高: 2 };

// P0 先于 P1/P2；同优先级内低工作量优先，其次看预计提分，最后用标题保证稳定。
function byPriorityThenEffort(a: Revision, b: Revision): number {
  return (
    PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority] ||
    EFFORT_RANK[a.effort] - EFFORT_RANK[b.effort] ||
    b.gain - a.gain ||
    a.title.localeCompare(b.title, 'zh-CN')
  );
}
```

扣分处只做常量替换，数值不变：

```ts
value -= Math.min(DIMENSION_CAP, deducted);
```

排序放在标题去重之后、截断之前，并重排 id：

```ts
    .filter((r) => {
      if (usedRevisions.has(r.title)) return false;
      usedRevisions.add(r.title);
      return true;
    })
    .sort(byPriorityThenEffort)
    .slice(0, 6)
    .map((r, i) => ({ ...r, id: `v${i + 1}` }));
```
