# 答辩预演舱 · 旁白稿（白话版）

- 对应视频：`答辩预演舱-演示视频-无旁白.mp4`
- 时长：5 分 16 秒
- 录制：建议正常语速，不要播音腔；每段可单独录，后期按时间码对齐。
- 用词：全程不用“你”“你们”“我们”“大家”，不喊口号，不夸大。
- 语气：像给同学介绍一个自己用过的小工具，平实、具体。

## 时间码与旁白

### 00:00–00:05 · 开场卡

答辩之前，先做一次压力测试。

### 00:05–00:37 · 首页

这个作品叫答辩预演舱。这个程序不替人写材料，也不预测结果。这个网页的功能不复杂：读材料、找风险、排修改顺序。首页可以看到三位评审和最近的演练记录，点一下就能进入质询。

### 00:37–00:41 · 章节卡 01

第一步，先把材料拆开。

### 00:41–01:21 · 上传与材料体检

上传申报书、答辩稿或者论文。系统按章节切块，找出十几条最容易被追问的论点。每一条都标出证据强度和缺口：有没有基线，样本够不够，数字有没有出处。左边是材料体检，右边是论点清单。十二个最容易被问住的地方，按优先级排好。

### 01:21–01:25 · 章节卡 02

接下来，三位评审分别提问。

### 01:25–02:22 · 交叉质询

方法学教授关注实验能不能站住，会追问基线、样本和归因。产业评委关注成本、场景和壁垒。竞赛评审按规则看原创性、佐证和复现。问题旁边挂着材料原文，点开就能核对。答辩人只依据材料回答，材料里没写的内容，就答不出来。答不上来的地方，就是材料真正的缺口。

同一个问题，不同评审会从不同角度追问。先问结论，再问证据，最后问边界。整个过程是流式的，刷新页面也不会丢记录。

### 02:22–02:26 · 章节卡 03

质询结束，系统把问题整理成报告。

### 02:26–02:31 · 雷达定格

先看五维雷达。

### 02:31–03:12 · 报告

雷达把风险分成五个维度：创新、可行、证据、表达、合规。下面是风险清单，按严重程度排序，每条都能回到具体论点。再往下是修改清单，分成 P0、P1、P2，标出工作量和预计提升。这份报告的作用不是打分，而是告诉项目组，先改哪一条。

### 03:12–03:16 · 章节卡 04

最后，简单说一下过程。

### 03:16–05:08 · 开发过程

这不是一次性生成的代码。开发过程保留了五次比较大的调整。

第一次，把范围收窄。没有做通用 Agent 平台，只聚焦答辩这一个场景。

第二次，材料解析。早期版本把句首年份当成列表序号，二零二五年九月变成了年九月；后来收紧规则，并加了测试。

第三次，流式输出。最初会丢消息，刷新还会重复；改成先订阅再重放，并按消息编号去重。

第四次，评分校准。早期版本给示例项目六十六分，证据强度四十二，还有重复的风险项；后来给单维扣分封顶，并按标题去重，分数回到七十一。

第五次，构建环境。Windows 下依赖链接、esbuild 版本和命令入口都出过问题；最后改成 hoisted 安装和直接入口，评委可以按 README 复现。

这些记录都在 docs/prompts 和 Git 提交里。现在仓库里有三十多次提交、五个 Prompt 记录和一组单元测试。视频里的每个功能，都能在提交历史里找到对应改动。

### 05:08–05:16 · 收尾

这个作品叫答辩预演舱。这个程序不能保证答辩一定顺利，但可以让问题早一点出现。

## 录制建议

1. 先用手机备忘录按时间码读一遍，标记不顺口的句子，改成自己的说法。
2. 每段单独录，文件名用 `01开场.m4a`、`02首页.m4a`……后期按时间码拖进去。
3. 语速控制在每分钟 220–260 字；留半拍停顿，不要赶。
4. 不用刻意压低声音；正常说话，比“播音腔”更可信。
5. 如果某段太长，可以拆成两句，中间停 0.3 秒，后期不用剪。

## 需要避免的说法

- 不要用“你只需要……”“你一定……”“大家都会……”。
- 不要用“颠覆”“重构范式”“降维打击”这类大词。
- 不要承诺“保证通过”“评委一定喜欢”。
- 不要说“我们的系统多么强”；只讲这个作品做了什么、没做什么。
